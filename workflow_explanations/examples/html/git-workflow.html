Git merge vs. git rebase

Two ways to combine work, with different effects on commit history

Merge preserves existing commits and joins their histories. Rebase replays commits on a new base and gives them new commit IDs. Both can combine the same changes, but their history differs.

What history do we start with?

Suppose main and feature have diverged from commit B. These illustrative diagrams show arrows from older commits to newer commits.

  • feature points to E.

A branch name points to a commit. Moving that pointer differs from creating or replacing commits.

B

How does merge change history?

Run these commands to merge feature into main:

git switch main
git merge feature

Because these branches have diverged, Git creates merge commit M.

M has two parents: C and E. The main pointer moves to M. The feature pointer stays at E.

Existing commits keep their IDs and parent links. The graph retains both lines of development and records where they joined.

Fast-forward is another possible merge outcome

If the current branch is an ancestor of the incoming branch, Git can move the current branch pointer forward. This creates no merge commit. Use git merge --no-ff feature to request a merge commit when a fast-forward would otherwise occur.

C

How does rebase change history?

Start again from the original history. Run these commands to rebase feature onto main:

git switch feature
git rebase main

Git replays the feature commits after C. In this example, both feature commits contain changes that need replaying.

The feature pointer moves to E′. The main pointer stays at C.

D′ and E′ replace D and E in the feature branch's history. Their new parent links give them new commit IDs. Git does not edit the original commit objects in place.

A normal rebase produces a linear feature history here. It does not preserve merge commits by default. Git may omit commits whose changes already exist upstream or become empty.

Afterward, advance main to the rebased feature tip:

git switch main
git merge --ff-only feature

This succeeds if main has not diverged since the rebase. It moves main to E′ without creating a merge commit.

When should I choose each one?

Consideration Merge Rebase
Existing commit IDs Preserves them Replaces replayed commits with new IDs
Diverged history Joins branches with a merge commit Moves replayed work onto a new base
History shape Retains branch structure Usually creates a linear sequence
Shared branch Useful when others depend on existing commits Requires coordination if others use the rewritten commits
Local feature work Records how branches joined Useful for updating work before sharing it

Use merge when preserving shared history matters. Use rebase when you want to move your feature work onto a newer base. Follow the repository's collaboration policy.

Rebasing a published branch changes the history that collaborators may already use. Coordinate before rewriting it. Updating its remote branch may require a force push.

If your team authorizes that update, use git push --force-with-lease. Its lease check can reject an update when the remote differs from your expected state.

What happens when changes conflict?

Both operations can stop for conflicts. Rebase can stop several times because it replays commits individually.

Step During merge During rebase
Resolve Edit the conflicting files Edit the conflicting files
Stage git add <resolved-files> git add <resolved-files>
Continue git merge --continue git rebase --continue
Cancel git merge --abort git rebase --abort

Replace <resolved-files> with the actual file paths. Review the result and run relevant checks after either operation.

Skipping a commit drops its replay

Use git rebase --skip only when you intend to omit the current commit. It is not a general conflict-resolution command.
