TCP connection setup and teardown

Three messages establish a connection; each direction closes separately.

TCP uses a three-way handshake to exchange starting sequence numbers and confirm communication in both directions. A normal four-way teardown closes each direction separately. The four messages can sometimes combine into three segments.

How does the three-way handshake work?

The client starts an active open. The server listens for connection requests. Here, x and y represent their initial sequence numbers.

  1. The client sends SYN and enters SYN-SENT.
  2. The server acknowledges the client's SYN, sends its own SYN, and enters SYN-RECEIVED.
  3. The client acknowledges the server's SYN and enters ESTABLISHED.
  4. The server enters ESTABLISHED when it receives that ACK.

The server's reply combines SYN and ACK in one segment. The third segment can also carry application data.

The final ACK confirms that the client received the server's starting sequence number. Without it, the server cannot confirm receipt of its SYN.

B

What do sequence numbers and ACKs mean?

TCP numbers bytes independently in each direction. An acknowledgment identifies the next sequence number the receiver expects.

Item Sequence space consumed
SYN One sequence number
Data One sequence number per byte
FIN One sequence number
ACK without data, SYN, or FIN None

An ACK of x+1 acknowledges the SYN at x. If data starts at x+1 and contains n bytes, the next expected number becomes x+1+n.

An ACK confirms receipt by TCP. It does not prove that the receiving application processed the data.

How does the four-way teardown work?

Either endpoint can start closure. Here, the client closes first. The values u and v identify each endpoint's FIN sequence number.

  1. The client sends FIN and enters FIN-WAIT-1.
  2. The server acknowledges FIN and enters CLOSE-WAIT.
  3. The client receives that ACK and enters FIN-WAIT-2.
  4. The server sends FIN when its application finishes sending and enters LAST-ACK.
  5. The client acknowledges the server's FIN and enters TIME-WAIT.
  6. The server receives the final ACK and enters CLOSED.

FIN means that its sender has finished sending data. It does not immediately close the opposite direction.

These steps describe the normal path with a separate ACK before the server's FIN. Combined messages produce a shorter path.

D

Why does closure need two FINs?

TCP supports two independent byte streams. Each endpoint must announce the end of its own stream.

After receiving the client's FIN, the server can still send remaining data. The client can still receive that data during this half-closed state.

The server's ACK confirms receipt of the client's FIN. The server's later FIN announces the end of the server's stream.

Three segments are possible

If the server is ready to close immediately, it can combine its ACK and FIN in one segment. Closure then uses three segments.

An orderly FIN follows any earlier data in that direction. The receiver delivers end-of-stream after receiving the preceding bytes.

E

Why does TIME-WAIT exist?

In the normal teardown, the endpoint that sends the final ACK enters TIME-WAIT. This is usually the endpoint that initiated closure.

  • It can acknowledge a repeated FIN if the final ACK was lost.
  • It gives delayed segments from the old connection time to expire.

TIME-WAIT lasts twice the maximum segment lifetime, commonly written as 2 × MSL. The duration depends on the implementation.

After the timer expires, the endpoint enters CLOSED.

Lost final ACK

The server retransmits its FIN if it receives no ACK. The endpoint in TIME-WAIT can send the ACK again.

F

What can change the message pattern?

Situation Effect
Lost SYN or FIN TCP retransmits; captures may show more messages.
Lost handshake ACK A repeated SYN+ACK can trigger another ACK.
Simultaneous close Both endpoints send FIN; states and message order differ.
Connection reset RST aborts the connection instead of completing orderly FIN closure.

Three-way handshake and four-way teardown describe the usual logical exchanges. They do not guarantee exactly three or four packets in every capture.
